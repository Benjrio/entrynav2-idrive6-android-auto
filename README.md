# Wired Android Auto для BMW HU_ENTRYNAV2

**Русский** | [English](README_EN.md)

Проводной Android Auto: USB AOA → AA/TLS → H.264 decode → RGB через shared fd4 →
EGL/IVI в собственном окне HMI. Звук, микрофон и управление iDrive→AA пока
не реализованы. Сессия ограничена 1200 секундами.

Для сборки нужны локальные SDK, библиотеки ГУ и TLS identity. После клонирования
предоставить их по PRIVATE_INPUTS_RU.md.

## Состав

- `src/`: HMI native adapter, control IPC, USB receiver, producer и headers.
- `assets/`: HMI XML, manifest, текстовые/графические ресурсы.
- `runtime/aa/`: USB selection, reference TLS identity, decoder/TLS libraries,
  оригиналы 148 для проверки screen order.
- `vendor/`: полный локальный набор входов компилятора, без ссылок на соседний repo.
- `build.py`, `commands.json`: сборка четырёх ARM targets.
- `install-usb.sh`: установка и управление сессией OPEN/QUIE/status.
- `THIRD_PARTY_RU.md`, `third-party/`: сведения о стороннем коде,
  лицензии и исходники используемых библиотек.

## Сборка

Поддерживаемый экран ГУ — 1280×480; видео AA — 800×480.
Native adapter и scene reader требуют точного профиля HMI/библиотек.

Нужны Python 3.12+, LLVM clang и ld.lld, поддерживающие ARM Linux hard-float.
Это GNU/Linux ARMv7, не Android ABI. Проверено на macOS с LLVM из Android NDK
28.2.13676358; sysroot и GCC support уже находятся в vendor, NDK sysroot не нужен.
Windows: выполнять сборку внутри WSL с Linux LLVM/Python; файлы репозитория
должны сохранять регистр имён. Linux/WSL LLVM здесь отдельно не проверялся.

```sh
python3 build.py --cc /path/to/clang --ld /path/to/ld.lld
```

Если clang/ld.lld доступны в PATH: `python3 build.py`.
Можно задать `CC`, `LD_LLD` или `--out /absolute/output`.
Результат: `build/libOwnAndroidAuto.so`, `ownandroidauto-control.elf`,
`ownandroidauto-producer.elf`, `aa/hu-aa.elf`, ресурсы и `compile.json`.
Скрипт только компилирует, ARM-код не исполняет. После предоставления локальных зависимостей
сборка выполняется офлайн.

## Подготовка и запуск на HU

Native adapter проверяет точный ABI/build IDs из `src/profile.hpp`.
Путь установки и mount checks заданы в `install-usb.sh`: `/opt/app/cisu`,
`/dev/mmcblk0p6`, ext4. Это параметры поддерживаемой ГУ, не пути компьютера
сборки. Их изменение требует отдельной проверки профиля.
Работоспособность проверялась на версии HU 002_148_002.
После установки на HU необходим штатный перезапуск.

### Настройка своего телефона перед сборкой

В `runtime/aa/usb-device.conf` одна директива (`#` начинает комментарий). Файл
копируется в `build/aa/usb-device.conf`, а при установке в неизменяемый runtime,
поэтому выбор делается до первой установки. По умолчанию `any`.

| Директива | Что выбирает |
|---|---|
| `any` | любой телефон с Android Auto на любом USB-порту, если кандидат ровно один |
| `port 1-1 [2-1 ...]` | любой телефон с Android Auto, только на этих портах (до 4 путей sysfs ГУ) |
| `<USB-port> <VID> <PID>` | один конкретный телефон на одном порту (прежний формат, без изменений) |
| `auto` | только устройство, уже перешедшее в AOA accessory mode, `18d1:2d00`/`2d01` (прежний формат) |

`any` и `port` находят телефон без зашитого VID/PID в три шага:

1. **Фильтр только по sysfs** (`src/usb_discovery.h`). Читаются файлы атрибутов;
   узлы устройств не открываются, запросы не отправляются. Отклоняются: хабы,
   устройства Apple, устройства с интерфейсом накопителя, HID, принтера,
   смарт-карты, видео или Bluetooth, устройства с привязанным драйвером ядра,
   кроме драйверов модема телефона (`rndis_host`, `cdc_ether`, `cdc_ncm`),
   интерфейсы, занятые другим процессом через usbfs, и устройства без
   Android-подобного интерфейса (MTP/PTP, vendor-specific, например ADB,
   режим модема). Устройство также должно быть сконфигурировано и не меняться 1,5 с.
2. **Одно устройство или ничего.** При двух и более кандидатах ни одному ничего
   не отправляется (`ambiguous`); отключить лишний или использовать `port`.
3. **Один вопрос AOA.** Только этому устройству отправляется `GET_PROTOCOL`.
   Отказавшее устройство запоминается для этого перечисления и больше не
   опрашивается (переподключение сбрасывает); не более 3 за запуск. Дальше
   прежние строки, `START` и проверки повторного перечисления на том же порту.

Каждое решение пишется в `android-auto.log` как `USB_CANDIDATE ... verdict=...` и
`USB_AOA_PROBE ... result=...`. Чтобы увидеть выбор, ничего не отправляя, на ГУ:
`sh run-hu.sh usb-scan /tmp/ownandroidauto-kit-usb-01 [секунды]`
(`aa/usb-scan.elf`; код выхода 0 — одно устройство, 1 — нет, 2 — неоднозначно).
Прежняя строка `<USB-port> <VID> <PID>` работает как раньше: USB-port — имя
устройства в sysfs ГУ (`1-1`, `1-1.2`), VID/PID — по четыре шестнадцатеричные
цифры, как телефон показывает их **до** AOA accessory mode. Тесты на ПК:
`sh tests/run.sh` (Linux/WSL).

### Что требуется для универсальности

- Проверить фильтр `any`/`port` на машине: телефоны в режимах «только зарядка»,
  MTP и PTP; держит ли штатный медиаплеер MTP-телефоны через usbfs (тогда они
  отклоняются как `claimed-by-userspace`, и это правило нужно решить);
  собственные внутренние USB-устройства ГУ.
- Определить поведение при смене USB-топологии, сохранив отказ от
  неоднозначного захвата устройства.
- Проверить переход в accessory mode, повторное перечисление, отключение,
  освобождение интерфейса и повторный запуск на разных телефонах/версиях AA.
- Проверить совместимость согласования версии AA: `src/aa-phone-version.h`
  сохраняет поддержку наблюдавшихся ответов 1.1 и 1.7; другие версии требуют
  отдельной проверки протокола.
- Для разных ГУ отдельно подготовить проверенные ABI-профили и процедуру
  обновления runtime. Настройка телефона не снимает ограничения HMI/прошивки.

После сборки скопировать **содержимое build/** в новую директорию HU
`/tmp/ownandroidauto-kit-usb-01` через уже настроенный владельцем доступ.
Пароли, SSH-ключи, сетевые настройки и автоматическое подключение не включены.
В shell HU выполнить:

```sh
sh /tmp/ownandroidauto-kit-usb-01/run-hu.sh install /tmp/ownandroidauto-kit-usb-01
```

Installer сверяет HMI/ABI, узнаёт реальные Plugins paths через control inspect,
проверяет persistent mount и готовит регистрацию OwnAndroidAuto. Он сохраняет
существующие чужие файлы и не перезаписывает готовый runtime v24.
Если runtime v24 уже установлен, это **не механизм
обновления**: старые бинарники могут остаться активными. Для нового build сначала
нужен отдельный план версии/runtime path либо штатное удаление старой регистрации
при отсутствии загруженного модуля. Не копировать поверх отображённого DSO.

При REGISTRATION_PENDING (action23) дождаться следующего обычного полного старта
HU владельцем. Команд перезагрузки или PluginUnload/PluginLoad в комплекте нет.
После регистрации подключить Android-телефон USB-кабелем и выполнить:

```sh
sh /tmp/ownandroidauto-kit-usb-01/run-hu.sh open /tmp/ownandroidauto-kit-usb-01
sh /tmp/ownandroidauto-kit-usb-01/run-hu.sh status /tmp/ownandroidauto-kit-usb-01
sh /tmp/ownandroidauto-kit-usb-01/run-hu.sh stop /tmp/ownandroidauto-kit-usb-01
```

`stop` посылает QUIE, завершает собственные producer/receiver, освобождает USB
и свой слой. Для возврата в штатное меню используется физическая MENU.
Receiver отдельно не запускать: ему нужен унаследованный fd4 от producer;
producer запускается native adapter с приватным IPC/жизненным циклом.
USB takeover ограничен accessory interface0 с driver usbfs, не произвольными USB.
Логи: `/tmp/ownandroidauto-aa-*/android-auto.log`, summary.json, usb-transport.json,
`/tmp/ownandroidauto-native-*.log`, `/tmp/ownandroidauto-producer-*.log`.
Screen-order reader только читает процесс winston; атомарного CAS для общей
очереди слоёв нет, при несовпадении проверки producer прекращает запуск.
